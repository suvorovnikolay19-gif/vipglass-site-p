# VIP Glass — передача сайта дизайнеру и разработчику

Версия руководства: 16 октября 2026 года. Документ рассчитан на партнёра, разработчика или работу с исходниками в Claude Design. Все пути ниже указаны относительно корня переданного проекта.

## 1. Что передаётся

Это работающий статический прототип каталога VIP Glass: исходники интерфейса и данных, локальные изображения и шрифты, готовые HTML-страницы, генератор страниц, проверки и документация. Его можно изучать и изменять без доступа к исходному аккаунту ChatGPT Sites.

В проекте нет React, Next.js, сборщика JavaScript и обязательной установки npm-пакетов. Браузер загружает обычные ES-модули `.mjs`. Node.js нужен для проверок и предварительного создания статических HTML-страниц. В текущей среде использован **Node.js 24.19.0**; для воспроизведения удобно использовать Node.js 24.

Текущий опубликованный адрес: `https://vipglass.example`. Доступ ограничен настройками существующего Site. Передача архива сама по себе не передаёт права управления этим Site и не публикует внесённые изменения.

## 2. Как устроен сайт

`src/shell.html` содержит общую оболочку: шапку, меню, подвал, диалоги, подключения CSS и `app.mjs`. В исходной оболочке элемент `<main id="main">` должен оставаться пустым. HTML конкретной страницы создаёт общий рендерер приложения.

`dist/app.mjs` определяет текущий маршрут, вызывает нужный UI-модуль и связывает формы, поиск, галерею и проект. Внутренняя навигация использует History API (`pushState`, `popstate`). Поддерживаются прямые пути, например `/catalog/partitions`, и старые ссылки вида `#/catalog/partitions`. Если имеется маршрутный hash `#/…`, он имеет приоритет; без него читаются `location.pathname` и `location.search`.

Параметры фильтров находятся в query string. Например, `/catalog/partitions?pick=1&system=loft&opening=sliding` открывает подбор с пересечением этих условий. Query-параметры не создают отдельные страницы в sitemap. Совместимые старые адреса разрешаются в актуальные узлы, сохраняя переходы из ранее отправленных ссылок.

`build-pages.mjs` запускает настоящий рендерер в Node VM, получает готовый HTML каждой страницы и записывает его как `dist/<путь>/index.html`. При прямом открытии сервер сразу отдаёт содержимое страницы; после загрузки модулей интерактивная навигация продолжает работать в браузере. У каждой канонической страницы есть H1, title, description, canonical и структурированные хлебные крошки. Alias-файлы получают canonical своей актуальной страницы и не включаются в sitemap.

Это приложение без сборки JavaScript, но с отдельным шагом генерации HTML. После изменения данных, шаблонов или оболочки HTML нужно сгенерировать заново.

## 4. Как вносить изменения

### Текст, оформление и существующая страница

1. Найти текст в исходных `.mjs` или `src/shell.html`, а не в тысячах готовых HTML. Для локального поиска подойдёт `rg "фраза" dist/*.mjs src/shell.html`.
2. Изменить данные или соответствующий UI-шаблон. Название/описание исполнения обычно находится в дереве, FAQ — в `page-content.mjs`, общий экран — в `app.mjs` или профильном UI-модуле.
3. Для изменения дизайна править CSS и шаблон. Сохранить `id` форм, `data-*` атрибуты и имена полей, на которые опираются обработчики и тесты.
4. Запустить профильные проверки, затем `node build-pages.mjs --check` и сборку. Посмотреть результат в браузере на большом и узком экранах.

Для Claude Design удобно передавать весь исходный архив, указывать точные страницы и визуальную задачу. Просить менять исходники и возвращать изменённые файлы либо patch. Массовая замена сгенерированных HTML не является устойчивым способом изменения этого проекта.

### Новый раздел или исполнение каталога

Обычная ветка дерева имеет устойчивый `id`, `title`, содержательный `intro` и непустой массив `children`. Конечное исполнение конструкции имеет `kind: 'solution'`, существующий `solutionId` из `catalog.mjs` и конкретный `preset`. Если создаётся новый базовый тип изделия, его сначала нужно добавить в `catalog.mjs`. Индексатор отвергает пустые ветки, повторные пути и конечные страницы с неизвестным базовым типом.

Для нового исполнения проще взять ближайший **семантически подходящий** объект в дереве и изменить его свойства. Не создавать все возможные комбинации автоматически: часть толщин, механизмов и материалов несовместима. Путь формируется из цепочки `id`; смена `id` меняет URL, название — нет. Для перегородок сохранять `modelKind` и поля `preset`: систему, назначение, открывание, стекло, цвет, обработку, остекление, декор и жалюзи. Значение `project` означает, что параметр ещё не выбран.

Материалы и производство индексируются автоматически из своих деревьев. Лист определяется отсутствием детей. Свойства материала используются фильтрами: написание значений должно совпадать с уже принятыми значениями. Фурнитура задаётся отдельным списком: `applications` определяет допустимые конструкции, `type` — группировку, `finishes` — действительные доступные отделки. Зеркал в `applications`, подборе и каталоге фурнитуры нет. Артикулы и служебные коды поставщиков запрещены в публичных данных, карточках, поиске, формах, сохранённом выборе и экспорте; техническое происхождение фотографии остаётся в служебной документации. Из названий поставщиков публично разрешён только Pauli.

Перенос существующего раздела требует alias старого пути на новый. Для душевых и перегородок используются `showersPathAliases` и `partitionsPathAliases`; они подключены в `catalog-tree.mjs`. Для услуг — `productionPathAliases` через `resource-catalog.mjs`. Старый префикс `/production/materials` также поддерживается. Alias должен вести на существующую каноническую страницу, а не создавать отдельный дубликат. Контрольные старые пути хранятся в документах baseline и проверяются тестами.

### Полностью новая самостоятельная страница

Нужны три согласованные части: рендерер и маршрут в `app.mjs`, регистрация страницы в `build-pages.mjs`, ссылка из подходящего меню/раздела. Для нового модуля подключить импорт и, при необходимости, CSS в оболочке. Добавить метаданные и поведение очистки обработчиков при смене маршрута. Новый элемент дерева каталога регистрируется в сборке автоматически; отдельный специальный маршрут — нет.

Генератор и часть тестов выделяют рендерер по существующей границе startup-кода `app.mjs`. Если полностью перестраивается запуск приложения, нужно согласованно обновить VM-harness, а не удалять его проверки.

### Изображения и их смысл

Интерьеры находятся в `dist/assets/interiors/`, образцы и детали — в `dist/assets/production/`, новые изображения конкретных исполнений — в `dist/assets/exact/`. Для сгенерированного каталожного изображения используется пара `<key>.webp` и `<key>-480.webp`; текущая серия — 1254 × 1254 и 480 × 480. Реальные фотографии поставщиков сохранять без выдуманного увеличения исходного разрешения. Для нового изображения проверить обе версии, их реальный визуал и размер файла.

Точная привязка конструкции задаётся в `exact-catalog-media.mjs`: ключ — полный канонический путь страницы, значение — отдельное визуально проверенное изображение и его описание. `catalog-media.mjs` подключает этот реестр через `mediaAssets` и использует его в `mediaForNode`, `photoMarkup`, `galleryMarkup` с приоритетом перед общими подборками. Не наследовать точное изображение автоматически от родителя или соседнего исполнения. Для каждой страницы сверять число стёкол, открывание, положение петель, неподвижные доборы, форму, цвет, материал и видимые элементы комплектации с её `preset`.

Общие подборки в `catalog-media.mjs` пока остаются для неподготовленных страниц, но не считаются выполнением требования. Образец стекла должен соответствовать конкретному виду: серое рифлёное — серому рифлёному, дерево — деревянному поручню, складное открывание — складной механике. Поле `kind` отличает интерьер, образец и деталь; `src` и `thumbnail` позволяют использовать другой каталог assets. Новому ключу нужны правдивые `alt` и `caption`; подпись не исправляет неподходящую фотографию.

Для материалов, услуг и фурнитуры точка изменения — `resourceMediaForNode` и `resourceMediaAssets` в `resource-media.mjs`. Галереи передают реальный `data-resource-src`, чтобы увеличение не открывало прежний файл из наследуемого `node.image`. Проверять одновременно карточку, основную галерею и увеличение. Для фурнитуры разрешены **только оригинальные изображения проверенных моделей из согласованных каталогов поставщиков**: собственная генерация механизма или замена похожим элементом запрещены. Официальные предметные рендеры допустимы с честной подписью, но не называются документальными фотографиями. Проверять модель, назначение, вид крепления и подтверждённые отделки по официальному источнику; отсутствие точного источника отмечать как незавершённую работу, а не закрывать общей картинкой.

В предыдущем проходе подготовлены 24 иллюстрации с миниатюрами. Их происхождение и промпты: `docs/catalog-photos-a.json` … `catalog-photos-e.json`. Эти манифесты сохраняют историю, но не подтверждают соответствие нового требования каждому URL. Сгенерированная фурнитура из прежнего прохода не допускается вместо оригинальных изображений из официальных каталогов поставщиков. Привязки и аудит прошлого прохода: `docs/catalog-image-mapping-changes.json`, `docs/resource-image-mapping-changes.json`, `docs/image-coverage-audit.md`.

Текущий план — `docs/exact-image-plan.json`, 1 224 задания: 1 156 `pending`, десять `visual_verified`, 58 `supplierImageVerified`. Статус проверки источника фурнитуры не означает уникальную обложку каждого раздела. Десять точных изображений П-образных душевых уже подключены к трём веткам и семи конечным исполнениям. Манифесты `docs/exact-showers-branches.json`, `docs/exact-showers-sliding.json`, `docs/exact-showers-swing.json` перечисляют точные пути, промпты и проверенные видимые признаки.

Все 31 изделие фурнитуры используют оригинальные изображения из официальных каталогов поставщиков. Среди них три предметных рендера Pauli с подписью «Изображение из каталога Pauli»; не все исходники являются документальными фотографиями. Для 128 вариантов отделки — 122 точных изображения и шесть честно подписанных референсов. Локально сохранено 123 файла, включая дополнительное фото чёрного дерева. Подтверждённый источник, соответствие отделке и уникальность обложки — разные проверки; полная уникальность изображений по всему каталогу пока не достигнута.

При синхронизации точных изображений `sync-exact-media` считает `supplier-catalogue` (в том числе Pauli) подтверждённым источником изображения поставщика. Этот статус не доказывает фотографическую природу исходника или уникальность обложки страницы и не снимает отдельную проверку отделки.

### Портфолио, журнал и реальные материалы

Портфолио управляется моделью в `portfolio-data.mjs`: обложка, характеристики, точные связанные `productPaths`, этапы `before/during/after/review`, фото, видео и текст. На главной странице блок портфолио показывает только обложки готовых результатов и названия проектов; подписи и переключатели «До / В процессе / После / Отзыв» здесь не выводятся. Этапы остаются внутри страницы конкретного проекта, отсутствующие этапы не рисуются. Для постоянного обновления внести проверенные записи в исходные данные, добавить медиа, собрать и опубликовать сайт. Структура подробно описана в `docs/portfolio-content-model.md`.

`/content-editor` позволяет подготовить записи в браузере и экспортировать JSON. Его импорт/экспорт переносит **ссылки** на фото/видео, а не файлы медиа. Допустимы локальные `/assets/…` и разрешённые HTTPS-ссылки; временные `blob:`/`data:` не являются постоянным способом хранения. Экспортированный JSON нужно включить в исходные данные через существующую валидацию. Кнопка локального сохранения не меняет опубликованный сайт для других посетителей.

Для статей, историй и Reels менять `journal-data.mjs`, соблюдая модель из `docs/journal-content-model.md`. Видео требует прямого URL медиафайла и при необходимости poster. Ссылка на страницу видеосервиса не заменяет MP4. Автоматический импорт из социальных сетей не подключён.

## 5. Состояние пользователя и границы backend

| Данные / действие | Где находятся сейчас |
|---|---|
| Выбранные изделия, материалы, услуги, размеры, контакты и пожелания проекта | `localStorage`, ключ `vipglass-project-v1`, в текущем браузере и на текущем origin |
| Прикреплённые к проекту файлы | В памяти текущей вкладки; включаются в скачиваемый ZIP. После перезагрузки их нужно прикрепить заново |
| Экспорт проекта | Локальный TXT/ZIP через `project-utils.mjs`; отправки менеджеру автоматически нет |
| Черновик портфолио | `localStorage`, ключ `vipglass-portfolio-draft-v1` |
| Импорт/экспорт редактора | JSON для переноса данных; не серверная публикация и не загрузка медиа |
| Общие данные посетителей, CRM, почтовая отправка, серверная CMS | Не подключены |

Другой браузер, устройство или домен не увидит локальный черновик. Для переноса редактор предоставляет экспорт; для проекта — скачивание задания и файлов. `published` в локальном редакторе означает видимость в локальном портфолио/экспортируемом массиве, а не публикацию в общей CMS.

Фурнитура выбирается в составе совместимой конструкции, кроме зеркал, либо как пожелание к проекту. Отдельного заказа фурнитуры, интернет-оплаты, расчёта цены и склада здесь нет. Числовые толщина листа и ширина фацета сохраняются в проекте как числа и отражаются в текстовом экспорте; при переработке форм не превращать их только в декоративные подписи.

`normalizeSavedProject` в `project-state.mjs` мигрирует старые локальные данные: удаляет поля артикулов и источников поставщика; снимает фурнитуру с зеркал и отсутствующие в текущем каталоге варианты; очищает автоматически добавленные устаревшие строки, сохраняя собственный комментарий клиента. Общие пожелания к фурнитуре приводятся к действующим публичным названиям и доступным отделкам. `retiredHardwareRoutes` сохраняет девять удалённых адресов: семь зеркальных ведут в `/catalog/mirrors`, два адреса типа holder — в соответствующие разделы `/hardware/showers` и `/hardware/partitions`. Не возвращать исключённую зеркальную фурнитуру через импорт или старый localStorage и не сбрасывать весь проект клиента ради миграции.

## 6. Локальный запуск, проверка и сборка

Все команды выполнять из корня распакованного проекта. Установка npm-зависимостей не требуется. Для `tests-project-utils.mjs` дополнительно нужен `python3`: стандартный модуль Python проверяет содержимое созданного ZIP. Для остальных перечисленных Node-проверок отдельный Python-процесс не нужен.

```sh
node --version
node build-pages.mjs --check
node build-pages.mjs
```

`--check` рендерит и проверяет страницы, не записывая их. Обычный запуск после успешной проверки обновляет HTML, sitemap, robots и manifest. Вывод содержит числа страниц, aliases, ресурсов и состояние индексации. Не применять предварительную очистку `dist`: там лежат исходные модули и изображения.

Для просмотра в обычной среде получателя можно использовать любой статический HTTP-сервер с корнем **`dist`**. Например, если установлен Python 3:

```sh
python3 -m http.server 8000 --directory dist
```

Открыть `http://localhost:8000/`, затем проверить прямой глубокий URL и перезагрузку на нём. Не открывать HTML через `file://`: ES-модули и абсолютные пути рассчитаны на HTTP. Сгенерированные папки содержат `index.html`; сервер должен отдавать их как directory index. Публикация в подпапке другого сайта потребует изменения base/путей, сейчас проект рассчитан на корень домена.

### Проверки по назначению

| Команда | Что проверяет |
|---|---|
| `node validate-routes.mjs` | Маршруты, ссылки, чистые пути и legacy hash, неизвестные адреса, иерархию |
| `node validate-selection.mjs` | Выбор исполнения, формы, проект, числовые параметры, навигацию и галереи |
| `node validate-resources.mjs` | Материалы, услуги и фурнитуру, их фильтры и сохранение выбора |
| `node validate-granularity.mjs` | Достижимость детей/подвидов, сохранение старых адресов, подробность каталогов |
| `node validate-partitions.mjs` | Системы перегородок, aliases, AND-фильтры и толщину |
| `node validate-material-facets.mjs` | Совместимость фасетов, количества, исправление конфликтов фильтра |
| `node tests-project-utils.mjs` | Поиск, текст задания, экспорт и утилиты проекта |
| `node validate-portfolio.mjs` | Модель работ, медиаэтапы, фильтры и связь с изделием |
| `node validate-content-editor.mjs` | Настоящие обработчики локального редактора и импорт/экспорт |
| `node validate-journal.mjs` | Журнал, истории, архив и Reels |

Проверки используют реальный код в Node/VM и компактных DOM-harness. Они не заменяют браузерную оценку вёрстки. После дизайнерских изменений проверить меню, длинные заголовки, сетки, форму, фильтры, диалоги, клавиатуру, историю назад/вперёд, мобильную ширину и фактическую плавность сцены. В исходной рабочей среде поддерживаемый браузер был недоступен; подтверждённая проверка там ограничена Node и просмотром локальных изображений.

## 7. Публикация и текущие ограничения

Для обычного статического хостинга публикуется содержимое `dist` с сохранением структуры папок, корректной отдачей `.mjs`, CSS, WebP, MP4 и шрифтов. Исходники и тесты сохраняются отдельно для следующего изменения. Если меняется домен, обновить `origin` в `build-pages.mjs` и адрес canonical в `routeMetadata` внутри `app.mjs`, затем пересобрать страницы.

Публикацией существующего ChatGPT Site управляет его владелец или уполномоченный участник через соответствующий доступ. Получение ZIP не даёт такого доступа. Локальная правка, сборка, открытие в Claude Design или JSON-импорт редактора не обновляют существующий Site автоматически. Перед передачей на публикацию нужен конкретный проверенный комплект файлов; домен и аудитория управляются отдельно.

Сейчас сайт намеренно закрыт от индексации: `noindex,nofollow` в HTML и `Disallow: /` в robots. Генератор восстанавливает эти ограничения. Это отдельный слой от ограничения аудитории Site. Для публичного запуска потребуются решение владельца об открытии доступа, рабочий домен, подтверждённые коммерческие сведения/контакты, реальный канал приёма заявок и согласованное изменение индексации с пересборкой. Наличие sitemap не означает открытый SEO-запуск.

Полная замена изображений ещё не завершена. На части страниц остаются общие изображения семейств; это несоответствие обязательному требованию собственного точного изображения для каждого URL, а не разрешённый вариант оформления. Подпись с параметрами и предупреждение об иллюстративности не заменяют проверку геометрии и комплектации. План из 1 224 заданий ведётся в `docs/exact-image-plan.json`: 1 156 остаются `pending`, десять имеют `visual_verified`, 58 заданий фурнитуры — `supplierImageVerified`. Последний статус подтверждает изображения из официальных каталогов поставщиков, но не глобальную уникальность: обложки могут повторяться, шесть отделок показаны явно подписанными референсами. Три исходника Pauli являются предметными рендерами, а не документальными фотографиями. Сгенерированные конструктивные и материальные иллюстрации не подтверждают выполненный объект или производственные возможности. Собственная генерация фурнитуры запрещена. Артикулы не выводятся на сайте и в клиентском задании.

Портфолио, статьи и истории содержат явно обозначенные демонстрационные записи. Реальные работы, отзывы и производственные сведения должны поступить от владельца и заменить демонстрационные материалы. Общей CRM, серверного редактора, синхронизации между сотрудниками, загрузки файлов на сервер и автоматической соцсинхронизации нет.

Технические рамки ассортимента сохранять при редизайне: бесцветное стекло — нейтральное Crystal Vision; намеренная бронзовая/серая тонировка — отдельный выбор; SMART — внутренний слой триплекса; два ряда стекла в перегородке не обозначают герметичный стеклопакет. Утверждения о толщине, безопасности, производственных возможностях и совместимости нельзя выводить только из иллюстрации.
